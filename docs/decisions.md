# Architecture Decisions

Significant technical decisions made during development.

<!-- APPEND ONLY: new rows go at the bottom of this table, never inserted mid-table. If a row's context/rationale is too long for a table cell, create docs/decisions/<slug>.md and link to it from the table. -->
| Date | Decision | Context | Rationale | Consequences |
|------|----------|---------|-----------|--------------|
| 2026-03-04 | Tags live on Labels, not Entries | Needed correlations to work retroactively without re-tagging history | Tag a label "dairy" once; all past and future entries using it are included in correlation queries automatically | Correlation queries join through labels; entries themselves carry no tags |
| 2026-03-04 | Nested labels via self-referencing `parent_id` | Two-level hierarchies needed (body area → symptom, valence → emotion) | Avoids a separate category table; keeps queries simple; two levels is sufficient for all current entry types | Labels table is self-referencing; queries must handle parent/child relationships |
| 2026-03-04 | `seed_version` on all seed rows | App updates introduce new default labels and tags without overwriting user data | `INSERT OR IGNORE` + version gating allows safe incremental vocabulary updates across releases | All seed rows carry an integer version; migration logic must respect `is_default = false` rows |
| 2026-03-04 | `source_type` on Entry (log vs reflect) | End-of-day "reflect" logging is a future feature but needs a schema field now | Avoids a future breaking migration; reflect UI is deferred but the data model is ready | `source_type` is always `"log"` until reflect UI is built |
| 2026-03-04 | Local SQLite only — no backend | Privacy is a core product value, not just a technical default | All data on device; no accounts, no sync, no network layer | Export/import is the only device migration path; no real-time sync is possible |
| 2026-03-04 | One device, one person | Multi-user and multi-device sync would require a backend and account system | Keeps the product simple and fully private; no shared state to reason about | Users who switch devices must export then import manually |
| 2026-03-07 | Source files moved under `src/`; `@/` path alias for imports | `constants/`, `lib/`, and `__tests__/` were at the project root alongside `app/`, making the root noisy and the import paths inconsistent | Collocating all non-route source under `src/` aligns with React Native community convention. The `@/` alias (mapped in `tsconfig.json` and `jest` `moduleNameMapper`) replaces relative `../../` import chains. `app/` stays at root as required by Expo Router. | All new source files go under `src/`; imports use `@/` prefix; `app/` routes import components via `@/components/...` |
| 2026-03-04 | Custom migration runner using `user_version` pragma | expo-sqlite 55.0.10 (verified at install time) does not ship `migrateDbIfNeededAsync` — it is absent from the package source; third-party migration libraries add unnecessary complexity | Thin custom runner: read `PRAGMA user_version`, execute pending migration strings in transactions, increment version. Each migration is a plain SQL string in `lib/db/migrations/`. | Zero extra dependencies; migrations are plain SQL diff-able strings; version tracked natively by SQLite |
| 2026-03-04 | `better-sqlite3` for schema integrity tests | `expo-sqlite` requires a native module unavailable in Jest/Node | Schema integrity tests validate SQL correctness with `better-sqlite3` (synchronous, Node-native); they do not test the Expo module itself. This is a dev-only dependency. | Tests run in CI without a simulator; expo-sqlite behavior tested only in E2E (Maestro) |
| 2026-03-04 | Manual label merging is intentionally destructive | Users may create custom labels that duplicate a future default (e.g. "hot yoga" vs default "Yoga") — automatic fuzzy merging is too risky | Provide an explicit "Merge into…" flow in Settings: all entries using the custom label are repointed to the default label (gaining its tags retroactively), custom label is archived. Requires confirmation. Cannot be undone without re-creating the custom label. | Fuzzy/partial matches are never merged automatically; only exact case-insensitive matches merge at seed time |
| 2026-03-05 | Auto-increment IDs; UNIQUE on name for seed deduplication | Seed rows must be idempotent across app launches; explicit IDs are fragile — they require coordination as vocabulary grows and risk colliding with user-created rows | All seed tables use auto-increment PKs. `INSERT OR IGNORE` deduplicates on `UNIQUE(name)` (or `UNIQUE(entry_type_id, name)` for labels). Seeds never specify an `id` column. | User-created rows get auto-assigned IDs above the seed range naturally; future seed additions just supply a name |
| 2026-03-05 | Three-layer emotion hierarchy with arousal-based top level | Two-level flat hierarchy (Pleasant/Neutral/Unpleasant → specific emotions) conflated low-arousal pleasant states with neutral, and grouped very different negative experiences (Numb, Anxious, Panicked, Burned out) into a single "Unpleasant" bucket — losing signal for health correlations | Five top-level labels (Bright / Warm / Still / Heavy / Charged) map valence × arousal so users self-sort in one glance. A second layer of named emotions is the primary save point. A third layer offers granular specificity. Each level is saveable. Schema unchanged — `parent_id` self-referencing already supports N levels. | `entry-types.md` updated from "two-step" to "three-step" for Emotion. Seed data restructured: 5 parents → ~20 mid-tier → ~85 leaf labels. Arousal level now encoded in label placement, queryable via tag or parent chain. |
| 2026-03-05 | Physical is one entry type; one submission produces N entries sharing a timestamp | Energy, body area states, and whole-body states could have been separate entry types | One entry type keeps the logging flow unified and the schema simple. Multiple things logged in one session (e.g. energy + arm pain + clear-headed) are stored as separate rows with the same timestamp — no session/group ID needed. Timestamp proximity is sufficient for display grouping in Trace. | Physical logging screen handles all three modes internally; querying "all physical logs" is a single entry_type filter |
| 2026-03-05 | Energy folded into Physical as a label, not a separate entry type | Energy was initially a separate entry type with its own tile on the Tend grid | Energy is most useful when logged alongside other physical state observations. Nesting it inside the Physical flow encourages co-logging. Stored as a Physical entry with label `[Energy]` and `numeric_value` = 0–5. | One fewer entry type on the Tend grid; energy is not independently accessible without opening Physical |
| 2026-03-06 | Versioned `.sql` files for schema and seed migrations; custom Metro transformer to bundle them | Migration SQL was stored as TS string constants, making it hard to diff, syntax-highlight, or lint | Flyway-style `vN__description.sql` files live in `lib/db/migrations/`. A custom `sql-loader.js` Metro transformer wraps each file as `module.exports = <string>` so Metro can bundle it. Jest tests read the files directly via `fs.readFileSync` — no Metro needed in CI. `migrations/index.ts` is the ordered manifest; the runner in `database.ts` consumes it. | Adding a migration = create a `.sql` file + append to the manifest. The transformer is registered via `transformer.babelTransformerPath` in `metro.config.js`; removing it without updating the chain will break SQL imports silently. |
| 2026-03-05 | Universal Physical symptoms parented to `Body` label, not duplicated per area | UNIQUE(entry_type_id, name) on the label table prevents the same symptom name (e.g. "Pain") from existing under multiple body area parents | A dedicated `Body` parent label acts as the universal symptom pool. The UI loads `Body` children for every area selection alongside area-specific children. Clean DB queries: `parent_id = Body.id`. No schema change, no label duplication, no floating parentless symptoms. | `Body` is a structural label, not a user-selectable area. UI must filter it from the area picker. |
| 2026-03-07 | Physical state seed vocabulary is intentionally short; recents-first + search covers the rest | A comprehensive state list feels clinical and prompts self-diagnosis anxiety; users shouldn't scroll a medical index to find what they feel | Seed data provides a starting scaffold for common states. Recents surface first within each body area. A search bar and free-text "Add [query]" cover everything else. Custom states become part of the user's personal vocabulary and surface in recents over time. | Seed list stays short by design; future seed additions go through the `seed_version` mechanism |
| 2026-03-07 | Medical tags on physical state labels are deferred from MVP | Linking physical states to body systems (e.g. Headache → nervous-system) could power future insights ("your nervous system states correlate with poor sleep") but adds vocabulary curation work | Architecture already supports this — tags live on labels via `label_tag`, same mechanism as food tags. No schema change needed. Deferred until the seed vocabulary and tagging taxonomy are mature enough to do it well. | Future milestone: add medical/system tags to state labels as seed data; no UI change required |
| 2026-03-08 | Entry types have a separate user-facing `title` distinct from the internal `name` | `name` is used in code and the DB; the user-facing label needed to be softer and more evocative without changing the data model | A `title` column on `entry_type` holds the display string. Titles use UK English, infinitive register, and a soft/slightly magical tone consistent with Haven's voice. Final set: Sleep → **Slumber**, Hydration → **Replenish**, Food → **Nourish**, Emotion → **Unveil**, Physical → **Attune**, Activity → **Journey**. Icons carry primary meaning on the Tend grid; titles are secondary labels. | All UI must use `entry_type.title` for display. `name` remains the stable internal identifier used in code and queries. |
| 2026-03-09 | `dayjs` for timestamp capture and display | JS's `Date` has no method that returns local time with the UTC offset attached — `toISOString()` returns UTC, losing wall-clock time if the device timezone changes later | `dayjs` is small (~2kb), zero transitive dependencies, and good React Native track record. `dayjs().format('YYYY-MM-DDTHH:mm:ssZ')` captures local wall-clock time with offset in one call. Note: `dayjs(isoString).format()` still converts to the device's current timezone, so `formatEntryTime` reads the time components directly from the stored string to preserve the original wall-clock time. | All entry screens use `nowLocalIso()` on submit; Trace uses `formatEntryDate()` for grouping. Adding `dayjs/plugin/timezone` in future would allow full offset-aware parsing if needed. |
| 2026-03-11 | `queries.ts` is the single DB access surface — no screen calls `db.runAsync` directly | Screens and hooks accessing SQLite ad-hoc would scatter SQL across the codebase, making it hard to audit queries, test them in isolation, or enforce FK/transaction discipline | All SQLite access goes through named exports in `src/lib/db/queries.ts`. Screens and hooks call `getDb()` at the component boundary and pass the handle down. `db` is typed against a minimal interface (`Db`) satisfied by both expo-sqlite at runtime and `BetterSqliteAdapter` in Jest. | New query functions go in `queries.ts`; new app-facing shapes go in `query-types.ts`. Never import expo-sqlite directly in a screen or hook. Date comparisons in SQL use `substr(timestamp, 1, 10)` — not `strftime` — to preserve wall-clock local date. |
| 2026-04-15 | SQLite UNIQUE constraint detected via `msg.includes('UNIQUE')` on the error message string | expo-sqlite does not expose structured error codes; the only way to distinguish a UNIQUE constraint violation from other DB errors is substring-matching the error message | Standard SQLite emits `"UNIQUE constraint failed: <table>.<column>"` — the word `UNIQUE` is uppercase and stable across SQLite versions. A generic fallback message is shown if the string does not match, so a driver change degrades gracefully to the generic copy rather than crashing. | This pattern is currently used only in `FocusDropdown.handleSubmit`. Any future call site that needs to distinguish constraint errors should follow the same approach: check `msg.includes('UNIQUE')`, keep a generic fallback, and unit-test both branches. |
| 2026-04-14 | Two separate SQL string constants for filtered vs unfiltered queries in `getEntriesForTrace` | A single SQL string with conditional interpolation (`WHERE ${focusId ? '...' : '1=1'}`) mixes control flow into the query string, making injection risk harder to audit and both query shapes harder to read | Two named constants (`FILTERED_SQL`, `UNFILTERED_SQL`) share a common `SELECT` prefix and `TAIL` suffix; they diverge only on the `entry_focus` JOIN. The branch is at the call-site (`options?.focusId != null`), not inside the string. Both query shapes are statically auditable. | Future filtered queries on `getEntriesForTrace` (e.g. by entry type or date) should follow the same pattern: extend the options object, add a new constant, branch at call-site. |
| 2026-04-10 | `LogFormShell` centralises save state, Notes field, error, and confirmation across all log screens | Six log screens each maintained identical copies of `saving`, `saveError`, `showConfirmation`, and `notes` state — and the duplicate-entry bug (#111) existed because none had an in-flight guard | A single `LogFormShell` wrapper owns all four state values. `onSave` receives `{ notes?: string }` and throws on failure; the shell handles disabling the button during flight, showing `SaveConfirmation` on success, and `SaveErrorMessage` on rejection. Screens pass `canSubmit` and an async `onSave` callback — no save state remains per-screen. | All new log screen types should use `LogFormShell`. The Focus field extension (#134) will extend the shell's `extras` signature rather than adding per-screen state. |
| 2026-04-12 | `searchLabelsAcross` uses prefix-LIKE search across all entry types for the Focus label picker | The Focus label picker has no entry-type context — a user pinning "Headache" to a Focus should see it regardless of which log screen created it. The existing `getLabels(db, entryTypeId, ...)` contract is per-type and cannot serve this surface | `searchLabelsAcross(db, query, limit?)` issues a single `SELECT ... WHERE name LIKE ? || '%'` across the full `label` table with a default limit of 50 (screen overrides to 5 via `SUGGESTION_LIMIT`). Prefix-LIKE is case-insensitive on SQLite's default `NOCASE` collation for ASCII. The caller passes a small limit so the full-table scan cost is bounded per keystroke. | Use `getLabels` for per-type pickers (log screens). Use `searchLabelsAcross` only where the entry-type dimension is absent (Focus picker). Do not add a LIKE scan to hot paths without a `SUGGESTION_LIMIT` cap. |
| 2026-04-10 | Focus schema: composite PK on `entry_focus`, UNIQUE on `focus.name`, RESTRICT on `focus_label.label_id` | Focus is MVP one-focus-per-entry enforced at app layer; duplicate focus names would produce indistinguishable pills on Tend; silently losing pinned labels when a label is deleted would corrupt a Focus definition | `entry_focus` uses composite PK `(entry_id, focus_id)` for forward-compat if multi-focus is introduced later; app layer uses delete-then-insert, not `INSERT OR REPLACE`. `focus.name` is UNIQUE to prevent duplicate pills. `focus_label.label_id` is ON DELETE RESTRICT (not CASCADE) so label deletion is blocked if the label is pinned to a Focus — deletion must go through an explicit unpin. `focus_id` side remains CASCADE so deleting a Focus cleans up its label pins. | Label delete flows must check `focus_label` and prompt unpin before allowing deletion once label management UI exists. |
| 2026-04-13 | Focus pills row always shows `+ Add Focus` pill; named pills appear only when focuses exist | AC originally said "section absent when no active focuses" — but hiding the row entirely leaves new users with no path to create their first Focus from Tend | `+ Add Focus` is navigation chrome, not a focus pill. Named pills render only when `useFocuses` has results; the add pill is unconditional. The `/focus/[id]` route is intentionally wired but dead until #135 (Focus quick-log) ships — Expo Router shows a "not found" screen rather than crashing. | Named focus pills gated behind `!loading` check inside the ScrollView so the add pill is visible immediately on cold launch |
| 2026-04-14 | `ChipTray` extracted as a shared presentational component replacing inline chip rows | Six log screens plus `create.tsx` each owned an identical `View style={chipTray}` + `chips.map(<Chip>)` block — 7 copies of the same layout and style | Single `ChipTray` component owns the flex-wrap row and delegates chip rendering. `onRemove` is optional so the same component serves editable screens and read-only contexts (Trace expanded row). Callers guard `chips.length > 0` before rendering — the component does not return null internally so emptiness is an explicit caller concern. | All new screens that display a removable chip row should use `ChipTray`. Read-only chip rows (Trace, future Weave) omit `onRemove`. |
| 2026-04-14 | `FocusDropdown` opens a name-only inline modal for "+ New Focus" instead of navigating to the Create Focus screen | Navigating away from a log screen mid-entry loses unsaved form state; returning from a pushed route cannot auto-select the newly created Focus without routing tricks | The dropdown renders a React Native `Modal` (transparent, slide animation) with a single text input. On submit, `createFocus` returns the new ID, which is passed directly to `onSelect` — no routing needed, no state lost. The full Create Focus screen (from #132) remains for the Tend flow where label pinning matters. | Any other "create inline while mid-form" patterns should follow this modal approach. The modal only captures the name; full configuration happens later from a dedicated screen. |
| 2026-04-15 | Long-press on Focus pill opens edit; Settings is the archived-Focus management surface | Focus needed an edit entry point that didn't clutter the Tend dashboard with a persistent icon | Long-press on a pill navigates to the edit screen (consistent with other secondary affordances in the milestone). Settings → Focus section lists active focuses (with gear icon → edit) and archived focuses (with unarchive). The Settings path is the primary and discoverable route; long-press is a power-user shortcut. | Future Focus UI should honour this pattern: gear/settings icon in Settings as the canonical management surface, long-press as a secondary shortcut. |
| 2026-04-16 | `saveEntryBatch` inlines `saveEntry`'s INSERT rather than calling `saveEntry` in a loop | `saveEntry` wraps each call in its own `withTransactionAsync`; nesting `withTransactionAsync` throws "cannot start a transaction within a transaction" in both expo-sqlite and the Jest adapter | The batch function holds one outer transaction and repeats the insert steps inline. A comment inside `saveEntryBatch` cross-references `saveEntry` so any future column addition to the entry INSERT is mirrored in both places. | Any screen that needs to create N entries atomically should call `saveEntryBatch`, not loop over `saveEntry`. If a new column is added to the `entry` INSERT in `saveEntry`, it must also be added in `saveEntryBatch`. |
| 2026-04-16 | Focus quick-log screen (`focus/[id]/index.tsx`) is exempt from the `LogFormShell` mandate | The quick-log screen's interaction model — a pre-populated checklist that submits N entries in a batch — has no Notes field, no FocusDropdown (the Focus is the screen's subject, not a field), and no per-entry confirmation; `LogFormShell` would add irrelevant UI | Batch-operation screens are exempt. New log screens for single entry types must still use `LogFormShell`. | Future changes to quick-log's save state, error display, or in-flight guard must be handled inside `quick-log.tsx` directly rather than relying on shell infrastructure. |
| 2026-05-24 | Complete Routine screen (`routine/[id]/complete.tsx`) is exempt from the `LogFormShell` mandate | Same reasoning as Focus quick-log: batch semantics across N entry types, no FocusDropdown (Focus association is automatic from the routine definition), shared Notes field applies to all entries at once | `LogFormShell` is designed for single-entry-type logging; it cannot model a batch submit. In-flight guard (`submitting` state), error display, notes field, and save confirmation are handled inline in `complete.tsx`. | Second exempt screen — the exemption applies to any batch-submission screen. Single-entry-type log screens must still use `LogFormShell`. |
| 2026-04-16 | `isPhysical` helper identifies Physical rows via `entryTypeName === 'Physical'` string comparison | `FocusItem` carries `entryTypeName` but not `measurementType`; looking up the measurement type would require a DB join or an extended query type | The string `'Physical'` is the stable internal `entry_type.name` seed value (see `entry-types.md`). If the entry type name were ever renamed in the seed, Physical severity rows would silently disappear from the quick-log. The coupling is accepted as low-risk because the seed name is treated as a stable identifier throughout the codebase (same as `'Food'`, `'Activity'`, etc.). | Any screen that needs to branch on entry type identity should follow this pattern: compare against `entryTypeName`, treat the string as a stable constant, and document the assumption. |
| 2026-05-22 | Trace "Show context" switches to a full context view mode, replacing the filtered SectionList | Rendering context entries inline within each focal row caused duplicates when focus-matching entries appeared in both the filtered list and the context window; an in-place overlay also broke the causality story — users need to see all nearby entries together, not appended below one row | Tapping "Show context" sets `contextState: { focalEntry, entries }` (single state object) and replaces the SectionList with a flat FlatList of the ±2h window. Focus-matching entries render at full opacity (they are the anchors); non-focus entries render muted (opacity 0.45, they are the context). The focal entry gets a `colors.glow` left border as a position marker. Dismissing clears `contextState` and restores the filtered SectionList. No deduplication logic needed — the two views never coexist. | `contextState` is cleared on filter change, tab press, and `useFocusEffect`. The two-state predecessor (`contextMap: Map<number, …>`) is removed. |
| 2026-05-22 | Tab re-tap resets Trace filter via `useNavigation().addListener('tabPress')` from `@react-navigation/native` | Expo Router 4.x exposes no public API for "user tapped the already-active tab" events; the only path is the underlying React Navigation event | `@react-navigation/native` is a direct (non-transitive) peer dep of `expo-router` and is always present in the lockfile. The listener is registered once on mount with a correct `isFocused()` guard so first-visit navigation from another tab does not accidentally reset the filter. The `'tabPress' as any` type cast is required because Expo Router's typed navigation object does not expose this event in its public type — the eslint-disable comment explains the why at the call site. If Expo Router ever exposes a first-party API for tab press events, migrate to it and remove this pattern. | Used only in `trace.tsx`. Any other screen that needs tab-retap behaviour should follow the same pattern until a first-party Expo Router API is available. |
| 2026-05-22 | `routine_completion` uses an integer PK as the group key for routine completion events; entries carry `routine_completion_id` as a nullable FK | Completion state needed a group key to link a batch of log entries to a single "this routine was done" event; an earlier design proposed a UUID field | Integer PK follows the existing ID pattern across all Haven tables; `lastInsertRowId` from the `routine_completion` INSERT is immediately available and passed to the entry batch INSERT — no UUID library, no extra dep. `entry.routine_completion_id` is `ON DELETE SET NULL` so orphan entries remain valid individual log entries if a completion record is ever deleted. | Completion state per time block is derived at query time: join `entry.routine_completion_id → routine_completion.created_at` filtered by `routine_time_block.time_block`. Application code must insert `routine_completion` first and use the returned row ID when building the entry batch. |
| 2026-05-22 | `getRoutineCompletionState` counts completions from `routine_completion` directly; `substr(created_at, 12, 2)` for hour comparison | Could use strftime or a separate flag column on `routine_completion`; could join via `entry.routine_completion_id` | Counting `routine_completion` rows directly avoids N-per-item overcounting that would occur if we joined through `entry` (a single completion can link to multiple entries). `strftime('%H', ...)` normalises to UTC, defeating the wall-clock-preservation invariant. A flag column would require imperative updates on every block transition. Pure derivation at query time is stateless and testable with injected `today` param. `timeBlockWindow` in `queries.ts` is the canonical source of block hour boundaries — keep it in sync with `getTimeBlock` in `timestamp.ts`. | Any query that needs to filter by time-of-day on stored ISO strings must use `substr` not `strftime`. |
| 2026-05-23 | Routine item editing uses full-replace strategy (`replaceRoutineItems` deletes all then re-inserts) | Tracking individual item deltas (which items were added/modified/removed) requires diffing on the client and makes error handling more complex | Full-replace is correct because `routine_entry_type` rows have no external FK references (no `routine_completion` row references individual items). IDs change on every save, which is acceptable — nothing downstream relies on stable item IDs yet. If per-item completion tracking is introduced in a future ticket, the strategy will need to change to a delta approach. The routine item editor keeps a `DraftRoutineItem[]` local state array; on save the whole set is written in one transaction. | Future per-item completion tracking would require stable item IDs and a delta approach. Document this before building that feature. |
| 2026-05-23 | Archiving a routine from the edit screen requires no confirmation dialog | A confirmation interrupt (e.g. "Are you sure?") would conflict with Haven's calm-by-default interaction principles; however, archive is not immediately reversible from Tend (only from Settings) | Haven explicitly avoids interruption patterns. The Archive button is visually quiet (`variant="secondary"`, separated by a thin divider at the bottom of the form) — placement and styling signal low urgency. The action is recoverable from Settings → Routines at any time; no data is deleted. No confirmation dialog is shown. | If a future Settings → Routines unarchive flow is never built, this decision should be revisited — without that escape hatch, no-confirm archive would need a different treatment. |
| 2026-07-27 | `getTypedDb()` helper in `src/lib/db/typed-db.ts` centralizes the `SQLiteDatabase → Db` cast; call sites now `await getTypedDb()` instead of `(await getDb()) as unknown as Db` | ~40 call sites across 22 files repeated the compile-time-only double cast because expo-sqlite's `SQLiteDatabase` is structurally wider than the narrow `Db` query interface | Kept the helper in a new module rather than in `database.ts` so the ~25 jest module-factory mocks of `@/lib/db/database` (which list only `getDb`) need no changes — `typed-db.ts` is unmocked and delegates to the mocked `getDb`, and the cast is a runtime no-op so all existing tests pass unchanged | Pure refactor: no schema, migration, or runtime behaviour change. New callers should use `getTypedDb()`; `getDb()` remains for the migration/init path in `database.ts` |
| 2026-07-27 | Tend dashboard groups a Routine as "due now" once **any** configured time block has started, and never labels it overdue, missed, or skipped | Could drop a Routine out of the due list once its last block passed (a "missed" state), or show a count of blocks remaining | A Routine whose Morning block passed unfinished is still worth doing at 20:00 — removing it would turn Haven into a nagging to-do list and imply failure. Grouping is derived, never persisted: `groupRoutinesForDashboard` in `src/lib/utils/routine-dashboard.ts` sorts blocks Morning→Night, and because Night is only ever the *current* block (never a configured one) every configured block reads as started at night, so nothing silently disappears. Anything completed or still ahead collapses behind one disclosure row, and can still be completed early. Progress text shows the true completion count and is deliberately not clamped — a Routine done 3 times against 2 blocks reads "3 of 2" rather than hiding work the user did. | Copy in this area must avoid "overdue", "missed", "skipped", "behind", and "streak" — there is a guard test in `src/lib/utils/__tests__/routine-dashboard.test.ts`. Completion state is read twice per refresh (`getRoutineCompletionState` for grouping, `getRoutineDayProgress` for display); a future refactor could derive both from one read. |
| 2026-07-28 | The better-sqlite3 test adapter (`src/__tests__/db/adapter.ts`) normalises every thrown value into a realm-local `Error`, guarding on `Object.prototype.toString.call(err) === '[object Error]'` rather than `instanceof Error` | Reset better-sqlite3's private `addon.isInitialized` flag in a `setupFilesAfterEnv` file; replace `rejects.toThrow()` with a custom `expectRejection()` helper at 8 call sites; loosen the assertions to `.rejects.toBeDefined()`; pin test ordering or force `--runInBand` | better-sqlite3's `SqliteError` calls `Error.call(this)` instead of `super()`, so the `[[ErrorData]]` slot is never installed and `Object.prototype.toString` returns `'[object Object]'`. The native addon binds one error constructor process-wide while Jest gives each test file its own vm context, so the first db test file in a worker to open a Database hands the addon *its* `SqliteError` and every later file receives errors whose prototype chain reaches a foreign realm — making `instanceof Error` false. Jest's `rejects.toThrow()` gates on exactly that check and reports "Received function did not throw" for a promise that did reject, so a realm mismatch was indistinguishable from a genuine rollback regression (#179). The adapter is a double for expo-sqlite, which rejects with real `Error`s, so normalising closes a fidelity gap rather than weakening a test. The shape guard is used instead of `instanceof` because `instanceof` is the value that varies with load order — using it would let the first-loaded file skip wrapping and reintroduce the same asymmetry. | All four adapter methods wrap, not just `withTransactionAsync` — the duplicate-name failure comes from `runAsync` with no transaction involved. `src/__tests__/db/adapter-errors.test.ts` locks the contract in place and is the primary regression defence. Any future test double over a native module must check that thrown values are realm-local `Error`s. Synchronous `expect(fn).toThrow()` was never affected — only the async `rejects` path. If a future test awaits a raw better-sqlite3 call outside the adapter and asserts `rejects.toThrow()`, the flake returns. |
